# Deadline and Backup-Center Pilot

## Purpose

This is the first, fixed-instance experiment for studying whether single-crane dispatch choices affect urgent local order completion and the work transferred to a backup center. It evaluates schedules generated by FCFS, earliest due date (EDD), minimum estimated slack, nearest eligible pick, and the existing makespan-oriented ACO.

The ACO objective is unchanged. Deadlines are evaluation cutoffs: the crane continues its scheduled work after each order's deadline. This separates schedule quality under deadline pressure from future decisions about interrupting work or dispatching orders to a second center.

## Reproduction

Run from the repository root:

```powershell
python -m examples.ASRS.deadline_experiment --instance examples/ASRS/instances/demo_seed_42.json --seed 42 --repeats 5 --ants 12 --iterations 25
```

The generated files in `results/deadline_study/` are:

- `experiment_design.json`: instance path, random seed, deadline formula, and timing-model description.
- `deadline_policy_raw.csv`: each ACO run and its per-order due times and rescue counts.
- `deadline_policy_summary.csv`: mean results by method and deadline factor.

All orders are available at time zero. One seed generates a fixed random urgency ranking shared by every policy and deadline factor. For each order, due time is:

`FCFS reference makespan × deadline factor × urgency fraction`

Urgency fractions span 0.8 through 1.2. The supplied deadline factors are 0.75, 1.0, and 1.25. Thus the same order remains urgent across all methods; only the overall deadline pressure changes.

The policy schedules are evaluated by executing the ASRS controller and acceleration-profile crane in `asrs_devs.py`. The crane's motion parameters have not yet been calibrated against physical equipment. Greedy-policy dispatch estimates remain simplified; ACO schedule scoring uses the DEVS-measured cycle table described below.

## Cycle-time table

Generate the table with:

```powershell
python -m examples.ASRS.crane_cycle_times
```

The builder executes one-cell DEVS probe models for every rack cell. It saves 180 initial home-to-cell cycles and 360 repeated cycles indexed by start station, cell, and destination station. Each entry records box-out time and crane-ready time. The 10-unit controller startup delay is excluded from each entry and charged once by `evaluate_schedule`. `AntColonyOptimizer`, the single-crane ACO CLI, the animation, and the allocation-study runner use the table when it is available; use `--cycle-times` to select another compatible table.

For the default rack and current crane settings, a complete DEVS run of the 50-product heuristic schedule and the table evaluator produced last box-out times differing by about `1.6e-12` simulation units. This validates the table against the current model's cycle semantics, not against a physical crane.

Because all orders are released at time zero, the `FCFS` reference is operationalized as ascending order ID (the fixed input-order proxy). It is not a true online FCFS policy; that requires order arrival times and is reserved for a later experiment.

Additional rescue units in the table represent stock that exists locally but is not delivered by the order's deadline. ## Sixteen-instance comparison

The same experiment was rerun on the 16 fixed allocation-study instances, now with ACO scoring schedules using the DEVS-measured cycle table. Each instance has its own input-order reference makespan and reproducible urgency ranking shared across policies. Five ACO search seeds were run per instance; the same ACO schedules were replayed for all three deadline factors. Reported 95% t intervals are calculated across the 16 instance-level results after averaging ACO seeds within each instance. They describe variation across this designed set of cases, not a random sample of all warehouses.

| Deadline factor | Policy | Complete by deadline / 10 | Rescue units | Change in rescue units vs. FCFS (paired 95% CI) |
| ---: | --- | ---: | ---: | ---: |
| 0.75 | FCFS | 6.00 | 19.50 | reference |
| 0.75 | EDD | 6.31 | 13.12 | -6.38 [-8.45, -4.30] |
| 0.75 | Minimum slack | 6.31 | 12.94 | -6.56 [-8.16, -4.96] |
| 0.75 | Nearest pick | 5.88 | 18.06 | -1.44 [-3.26, 0.39] |
| 0.75 | Makespan ACO | 6.75 | 17.15 | -2.35 [-3.75, -0.95] |
| 1.00 | FCFS | 7.25 | 7.88 | reference |
| 1.00 | EDD | 7.56 | 5.00 | -2.88 [-4.63, -1.12] |
| 1.00 | Minimum slack | 7.56 | 5.00 | -2.88 [-4.63, -1.12] |
| 1.00 | Nearest pick | 7.12 | 7.50 | -0.38 [-1.56, 0.81] |

| 1.25 | Makespan ACO | 8.25 | 5.09 | 0.09 [-0.02, 0.20] |

The minimum-slack rule now includes elapsed estimated processing time and assumes a return to an unloading station after each item. It differs slightly from EDD under the tightest deadlines, while aggregate results coincide at the other two deadline factors.

The results show a service-versus-rescue tradeoff. Under the tightest deadlines, EDD reduces rescue units more than makespan ACO, while ACO completes more orders on time. At factor 1.0, EDD's paired rescue reduction versus the input-order baseline is 2.88 units with a 95% interval excluding zero; makespan ACO's 0.03-unit change has an interval spanning zero. Under the loosest deadlines, rule-based policies reach the unavoidable five-unit stock shortage; ACO averages 5.09 units. That small difference is within the across-instance interval and reflects stochastic schedule search, not a physical stock increase. Makespan-only ACO does not minimize rescue work under tighter cutoffs.

The cycle-table evaluator was checked against complete DEVS execution of a 50-product schedule: predicted and observed last box-out times differed by about `1.6e-12` simulation units. Across the 432 deadline-policy runs, the maximum absolute relative timing difference was below `3.4e-15`. This confirms that the table reproduces the current DEVS model for these schedules. It does **not** validate the crane parameters against physical hardware.

Files are in `results/deadline_study_16instances/`: the raw CSV contains 432 schedule/deadline observations, the summary CSV includes instance-level 95% intervals and paired deltas, and the design JSON records seeds and the deadline formula.

## Next work

1. Calibrate the DEVS crane's X, Z, and fork parameters, pickup delay, and unloading delay against manufacturer specifications or measured motion/cycle times.
2. Improve the minimum-slack baseline and confirm its behavior on additional urgency profiles.
3. Add order arrivals and releases over simulation time, then report mean and tail order response time, deadline service level, throughput, and backlog.
4. Add finite backup-center capacity and distinguish residual-SKU replenishment from full-order rescue.
5. Only after those measurements, add due-date and rescue terms to ACO and compare it with unchanged policies.
